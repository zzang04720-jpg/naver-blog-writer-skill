# search-post-writing

## 트리거 조건
`post-writer`가 S6에서 `01_brief.json`의 `track == "search"`를 확인했을 때. `homefeed-writing`과 동시에 로드하지 않는다 — 두 트랙의 도입부 규칙이 정반대이기 때문이다.

## 목적
검색 의도에 직응답해 누적 검색 자산을 쌓는다. 홈피드형과 달리 단기 체류시간이 아니라 장기적인 검색 유입이 목적이다.

## 핵심 작문 규칙
1. **도입부에서 결론을 먼저 준다.** 검색해서 들어온 독자는 답을 바로 찾는다. 첫 2~3문장 안에 핵심 답변의 방향이 드러나야 한다 — 홈피드형과 정반대 원칙
2. **이후 근거와 조건·예외를 확장한다.** 결론 뒤에 "왜 그런지", "예외는 무엇인지"를 소제목으로 나눠 풀어간다
3. **콘텐츠 갭을 독립 소제목으로 배치한다.** `01_brief.json`의 `gaps[]`에 담긴, 상위글이 다루지 않은 하위 주제를 최소 1개 이상 별도 소제목으로 만든다 — 이게 이 글이 상위글과 차별화되는 지점이다
4. **1차 출처 기반 정보는 재진술한다.** `01_brief.json`의 `primary_sources[]`에서 확보한 사실(수치·데이터·조건)은 문장을 그대로 옮기지 않고 새로 풀어쓴다. 경쟁 블로그 문장도 마찬가지다 (S7 검증 항목 2)

## 공통 제약
네이버는 개별 글의 메타 설명 입력란이 없고 본문 앞부분이 검색 결과 요약으로 자동 노출된다. 검색형은 원래 도입부에서 즉답하는 구조라 이 제약을 별도로 신경 쓸 필요가 적지만, 첫 문장이 키워드·대상과 무관한 미사여구로 시작하지 않도록 주의한다.

## AI 문체 회피 — 톤 예시 참고 (하드 게이트)

**`references/sample-good-tone.md`를 반드시 참고한다.** 홈피드형 예시지만 기법 자체는 트랙과 무관하게 적용된다: 나열 항목의 비대칭(4단계 세정법처럼 항목마다 문장 수·길이가 다름), 짧은 문장으로 끊어 강조("겉면만입니다."), 주관 개입 한 스푼("개인적으로는..."). 검색형은 도입부에서 결론을 먼저 주고 조건·예외를 나열식으로 풀다 보니 특히 **나열 비대칭**에 취약하다 — 조건 목록·비교 항목·가입 절차 같은 것을 쓸 때 모든 항목을 같은 길이·같은 문형("~을 ~한다")으로 채우지 않도록 의식적으로 신경 쓴다.

작성 시 아래 4개 세부 체크를 스스로 맞춰본다 — S7에서 항목 7로 재검증되며, **이번 개정부터 위반 시 통과되지 않고 재작성 대상이 된다.**

- **서술어 다양화**: 같은 서술어(용언)가 연속 3문장 이상 반복되지 않게 쓴다. 종결형 자체(-습니다, -다 등)를 문서 전체에서 통일하는 것은 허용된다 — 정상적인 격식체 선택이지 AI 티가 아니다
- **나열 비대칭**: 번호 목록이나 항목 나열을 쓸 때, 모든 항목을 같은 길이·같은 문형으로 채우지 않는다
- **문장 길이 대비**: 한 문단 안에 짧은 문장(5어절 이하)과 긴 문장(20어절 이상)이 둘 다 있도록 쓴다
- **구체성 삽입**: 문단마다 최소 하나는 구체적인 디테일(시간, 상황, 수치, 감각 묘사 등)을 넣는다

이 외에 `blog-profile.yaml`의 `banned_expressions`에 있는 표현은 쓰지 않는다.

## 출력 형식
`02_draft.md`에 제목 + 소제목 3~5개(콘텐츠 갭 소제목 포함) + 본문 + 이미지 삽입 위치를 남긴다. 분량은 공백 포함 2,000~3,500자.

## 경로 기준

위 실행 명령은 저장소 루트에서 실행한다. `references/`와 `assets/`는 이 SKILL.md가 있는 폴더 기준이다. 다른 런타임에서는 `.claude/skills/` 대신 `.agents/skills/`의 동일한 스크립트를 사용할 수 있다.
